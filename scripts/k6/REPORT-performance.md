# تقرير نطاق تحسين الأداء — منصة Binaa

**التاريخ:** 2026-08-06
**المرجع:** اختبارات k6 (Smoke / Load / Stress) — التقارير الكاملة في `scripts/k6/REPORT-read.md` و`REPORT-write.md`
**الأعراض:** SSR p95=40s وREST 4–28s عند 200 مستخدم متزامن، أخطاء 5–11%، إنتاجية مشبعة ~200 طلب/ث، الأصول (CDN) غير متأثرة، Auth محدود ~30/ساعة/IP.

| # | المجال | المؤشر | الاقتراح | الأولوية |
|---|---|---|---|---|
| 1 | **اتصال قاعدة البيانات** | مشبعة ~200 req/s عند 200 VU — نمط نضوب تجمّع اتصالات | تفعيل **Transaction/Connection Pooler** في Supabase (Database → Connection pooling)؛ رفع عتبة الاختبار لتحديد السقف الجديد | عالية |
| 2 | **الفهارس** | الرحلات تصفّي `project_id` + ترتيب `created_at desc` | تأكيد فهارس `tasks(project_id, created_at)` و`projects(created_by, created_at)`؛ فحص SEQ Scan عبر EXPLAIN في SQL Editor | عالية |
| 3 | **SSR/Serverless** | p95=40s — أبطأ مسار (صفحات المشاريع/التفاصيل) | مراجعة `maxDuration` ومنطقة الوظائف ونقاط البرودة؛ تفعيل `revalidate`/ISR للصفحات العامة بدل SSR كامل | متوسطة |
| 4 | **Notifications API** | p95=828ms حتى في smoke (أعلى من بقية الواجهات) | إضافة ذاكرة مؤقتة، أو القراءة عبر عميل Supabase مباشرة بدل route handler | متوسطة |
| 5 | **Auth rate limit** | 30 تسجيل/ساعة/IP | قيد أمني مقصود من Supabase — يُبقي عليه؛ يعرقل فقط تسجيل الدخول الجماعي | منخفضة (لا تغيير) |
| 6 | **الأصول الساكنة** | سليمة تحت كل الأحمال | لا تغيير | — |

## ملاحظات قياسية
- القياس قبل أي تغيير: `npm run test:stress` بعد تنظيف بيانات `[LOADTEST]`.
- أعد القياس بعد كل بند على حدة لمعرفة أثره الحقيقي، ولا تُطبق كل التحسينات معاً قبل عزل الأثر.

## خلاصة
المنصة آمنة حتى ~100 مستخدم بجودة مقبولة (Stress: p95 SSR <3s). النضوب عند 200 يُرجَّح سببه تجمّع الاتصالات وليس الواجهة نفسها — البدء بالبندين 1 و2 يعطي أكبر أثر بأقل تغيير.
