# خطة إصلاح «القوائم الفارغة» بعد ميزة الأدوار — PLAN MIGRATION

> سجل قرارات مُعتمدة من المالك. يُنفَّذ كمرجع لا يُتجاوز دون موافقة.

## المشكلة (Root cause)
- commit `548d02f` غيّر نطاق قراءة القوائم من `user_id` إلى `company_id` (multi-tenant).
- `tasks/plan.md` وعد بترحيل: «شركة واحدة + عضو owner نشط لكل مستخدم قديم» عبر مُفعِّل
  `handle_new_user` — **لكن لم تُرفَع أي مهاجرة (migration) إلى المستودع**:
  الوحيدة المرفوعة هي `20260913120000_create_contact_messages.sql`.
- النتيجة: البيانات القديمة بلا `company_id`، وتُقرأ القوائم بـ
  `if (!companyId) return []` في `workers-service` و`equipment-service` → قوائم فارغة.

## القرارات المعتمدة (من المالك، 2026-09-18)
1. **الخيار A**: نُبقي نموذج الشركات ونرحّل البيانات — لا نعود لـ `user_id` خالص.
2. **السكربت يكتبه المطوّر** (هذا الملف) و**يشغّله المالك يدوياً** في Supabase SQL Editor.
3. **اسم موحّد** للشركات المُنشأة تلقائياً — يُعدَّل في نقطة واحدة فقط
   (دالة `binaa_default_company_name()` أعلى المهاجرة). الافتراضي: `شركة المقاولات`.
4. **قراءة تعويضية غير صامتة**: عند غياب العضوية تُقرأ القائمة بمدى الحساب الشخصي
   (`user_id`)، مع إشعار واضح في الصفحة — لا `return []` صامتة.
5. **النطاق ضيّق**: لا لمسَ لسلوك نافذة العمل دون اتصال (خارج الطلب).
6. **RLS**: التحقق فقط في المهاجرة — تعديل السياسات يبقى قراراً يدوياً منفصلاً.

## التنفيذ

### 1) المهاجرة `supabase/migrations/20260918120000_fix_company_ownership.sql` (idempotent)
- تشخيص قبل/بعد بعدّادات صريحة.
- إنشاء `companies` / `company_members` فقط **إن غابت** (+ أعمدة/فهرس إن غابت).
- إنشاء `handle_new_user` + trigger `on_auth_user_created` **فقط إن لم يوجدا**
  (لا استبدال لشيء قائم). المفعّل يمنح الشركة الشخصية **إلا** إذا كان المستخدم:
  1) منشأً بواسطة مدير (`app_metadata.is_admin_created=true` — عقد `team-admin-service`
     خط 77: الحسابات المدرية لا تأخذ شركة خاصة؛ المستخدم يلتزم بعضوية الشركة التي
     أضافها المدير)، أو 2) عضواً نشطاً ببريد ما — فالمرتبط بشركة مدير لا يأخذ شركة خاصة به.
- ترحيل: شركة + عضو `owner` لكل مستخدم بلا عضوية (حساباً أو بريداً)، ثم ربط
  الصفوف اليتيمة في `workers` (عبر `user_id`) و`equipment` (عبر `user_id`)
  و`projects` (عبر `created_by`) بأول عضوية نشطة.
- تحقّق ختامي يعرض العدادات ويوضّح أن RLS لم تُعدَّل.

### 2) الكود — تعويض القراءة (دون لمس الإضافة/الحذف)
- جديد: `src/lib/services/user-scope.ts`
  - `resolveCurrentUserId()` — مصدر واحد لهوية الجلسة (كان مكرَّراً في كثير من الخدمات).
  - `resolveMyDataScope()` — `{ userId, companyId }` بالتوازي.
- تعديل `workers-service` و`equipment-service` (getAll):
  الشركة إن وُجدت، وإلا `user_id = المستخدم` (بدل `return []`) + تعليق يشرح لماذا.
- `projects-service` لم يتغيّر (يحوي مدى `created_by` أصلاً) — يستفيد تلقائياً من الترحيل.

### 3) الواجهة — وضوح الحالة بدل جدول فارغ محيّر
- جديد: `src/components/team/CompanyScopeNotice.tsx` — إشعار لون+أيقونة+نص
  عندما لا توجد عضوية، في صفحتي العمال والعتاد.
- `workers/page.tsx`: إفراغ جدول سطح المكتب الحالي (كان بلا حالة فارغة) +
  رسائل فارغة واعية بالفلاتر (جوال وسطح مكتب).
- `equipment/page.tsx`: توحيد حالة الفارغ عبر `DataState.Empty` (جوال وسطح مكتب).

### 4) التحقق
- `npm run lint` و`tsc` نظيفان.
- `npm run check:design` لا يضيف مخالفات عما هو قائم (العتبة الحالية معروفة).
- تحقق بصري 375 / 768 / 1440 على صفحتي العمال والعتاد.
- المالك يشغّل المهاجرة في SQL Editor ثم يتحقق من القوائم في الإنتاج.

## النقاط الحساسة للمراجعة الشخصية قبل القبول
1. مضمون المهاجرة: إنشاء المفعِّل والجداول — يُنفَّذ على قاعدة الإنتاج؛
   راجع قسمي (3) و(4) قبل التشغيل.
2. لا تُعدَّل RLS تلقائياً — تحقّق أن سياسات `companies`/`company_members`
   تمنع القراءة العامة لبيانات المستأجرين الآخرين.
3. فرضية «كل مستخدم قديم بلا عضوية = مالك شركة خاصة» — إن وُجد مستخدمون لا
   ينبغي أن يملكوا شركة خاصة، اعدّل قسم (4) قبل التشغيل.
